# e2e 結果まとめ(2026-10-12)

agent の検索処理を非同期化した修正の効果と、回答品質の現状値(基準値)をまとめます。
元データは [reports/2026-10-12/](reports/2026-10-12/) に置いています(`results/` は git 管理外のため、主な出力をコピーしたもの)。
実行方法は [README.md](README.md) を参照してください。

## 1. 同時アクセスのレイテンシ

- 内容: 修正前(同期)と修正後(非同期)で、同じ条件で測定
- 条件: 別アカウントのブラウザが、全員同時に質問を送る。同時接続数ごとに3回ずつ(1人=3件、5人=15件、10人=30件、20人=60件)。ローカルの docker compose 環境
- 修正の対象: [rag.py](../apps/agent/src/lib/rag.py)(`AsyncOpenAI` と `psycopg.AsyncConnection`)、[graph.py](../apps/agent/src/agent/graph.py)(`await vector_search`)
- 値は p50(中央値)、単位は ms。失敗は全条件で 0 件

| 同時接続 | 検索(埋め込み+DB) 前 → 後 | 回答開始 前 → 後 | 最初の文字 前 → 後 | 全体 前 → 後 |
|---|---|---|---|---|
| 1 | 254 → 139 | 1609 → 1436 | 2121 → 2311 | 2836 → 2771 |
| 5 | 823 → 169 | 2652 → 1674 | 3226 → 2246 | 4583 → 3275 |
| 10 | 1184 → 194 | 3950 → 1828 | 4615 → 2416 | 5978 → 3797 |
| 20 | 2354 → 253 | 7483 → 2643 | 8232 → 3296 | 10876 → 5808 |

分かったこと:

- 修正前は、同時接続が増えるほど検索の所要が直線的に伸びた(1人 254ms → 20人 2354ms)。同期呼び出しがイベントループを占有し、順番待ちになっていたため
- 修正後は、20人でも検索は 253ms で、ほとんど伸びない
- 1人のときはほぼ同じ。この修正は、単独の速度ではなく、同時アクセス時の待ちを減らすもの
- 修正後に残る時間(20人で最初の文字まで約3.3秒)は、主に LLM の書き換え・選別・回答の応答待ち

注意:

- 各条件3回の1回測定で、OpenAI の応答時間の揺れを含む。差が大きい検索の列は信頼できるが、「全体」の細かな差は誤差の範囲
- 最初の「修正後」の測定は、修正が反映されていないコードで走っていたため無効にして、測り直した。上の表は測り直した結果

## 3. 未対応・要確認

- **話題切り替え時の検索クエリ**: 書き換えのプロンプトで、前の会話を使うのは「続きの質問」のときだけにする
- **検索の取りこぼし(E09)**: 検索の上位8件にあったのか、選別で落ちたのかを切り分ける
- **確定申告の期限**: QA 707 と QA 702 の記述をそろえる(DBの修正)
- **範囲外の質問の方針**: 一般知識で答える設計のままでよいかを決める。変える場合は評価基準も合わせる
- **service から agent への通信にタイムアウトがない**([agent_client.py](../apps/service/infrastructure/agent/agent_client.py) が `timeout=None`)。止まると永久に待つ
- **基準値のぶれ**: LLM審判の採点は1回の実行で、揺れを含む。比較に使うときは同じ条件で2〜3回流す
- **接続は検索のたびに張っている**: 負荷が増えたらコネクションプールを検討する

cd e2e
