# テスト進め方

## 基本方針

- テスト仕様書（test_spec.md）に基づき、全148件を**4人で分担**して実施する
- 結果は test_spec.md の「結果」列に ○/× を記入し、不合格は「不具合一覧」にも記載する
- 1人あたり **約37件**（均等配分ではなく、画面単位で区切り関連テストをまとめて担当する）

## 進め方（Issue駆動）

テスト中に不具合を見つけてもその場では修正せず、**1周目を全員が最後まで回しきってからIssueを起票→修正→2周目で再テスト**する流れとする。

---

### ステップ1: 環境準備
1. `develop` ブランチをpull・最新化
2. `docker compose up -d` + `cd web && npm run start`でテスト環境を起動
3. テスト用ユーザーを作成（各担当で1アカウントずつ）
4. Chrome / Firefox / Safari / Edge を最新版に更新（担当Dは全ブラウザ必要）

---

### ステップ2: 1周目テスト実施（全148件を一通り回す）
1. 各担当が自分の割り当て項目を**上から順にすべて**実施する
2. test_spec.md の「結果」列に ○ / × を記入
3. × になった項目は「不具合一覧」テーブルにも記載する
   - 不具合No、テストNo、不具合内容、重要度（高/中/低）
   - **対応状況は「未対応」のままにしておく**
4. 判断に迷う場合は「備考」に状況を記載し、後でチームで確認
5. **不具合を見つけてもコード修正はしない。止まらず最後まで回す**

---

### ステップ3: 1周目結果の集約・Issue起票
1. 全担当の1周目テストが完了したら、結果を統合して**テスト結果サマリ**を更新する
2. × になった不具合を**GitHub Issue として起票**する
   - Issueの書き方は **docs/dev/IssueDriven.md** のチケットテンプレートを参照すること
3. 同じ原因の不具合は1つのIssueにまとめてよい（例: 複数画面で同じAPIエラーハンドリング漏れ）

---

### ステップ4: 不具合修正（Issue駆動）
1. 起票されたIssueを**重要度 高→中→低** の順に対応する
2. 修正は**Issueごとにブランチを切って**PRで対応する
   - ブランチ名: `fix/issue番号`（例: `fix/42`）
3. PRをレビュー・マージして `develop` に統合する
4. 修正が完了したIssueは対応状況を「修正済み」に更新する

---

### ステップ5: 2周目テスト（再テスト）
1. `develop` ブランチを最新化し、テスト環境を再構築する
2. **1周目で × だった項目のみ**再テストする
3. test_spec.md の「結果」列を更新する（○ に変われば合格）
4. まだ × が残る場合はステップ3〜5を繰り返す

---

### ステップ6: 完了報告
1. 全件 ○ を確認する
2. test_spec.md の「実施日」「実施者」を記入
3. 備考・特記事項があれば記載
4. テスト完了のIssueまたはPRで最終記録を残す

---

## 注意事項

- **1周目では絶対にコードを修正しない** — テスト結果の客観性を保つため
- **異常系テスト（API障害時等）** は他の担当のテストに影響しないよう、**1周目の最後にまとめて実施**する
- **E2Eシナリオテスト** は単体テスト項目をすべて回した後に実施する
- **ブラウザ互換性テスト（NF-15〜18）** は主要機能（ログイン→チャット→検索）の一連操作で確認
- **多言語テスト（ML-01〜10）** は全画面遷移しながら目視確認。文字切れ・レイアウト崩れも確認する
- **非機能テスト（NF-04〜09: セキュリティ）** はcurlやブラウザDevToolsで直接APIを叩いて検証する
